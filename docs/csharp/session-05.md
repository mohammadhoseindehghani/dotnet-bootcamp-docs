## هدف جلسه؛ پیدا کردن مسیر، نه حفظ کردن پاسخ

در این جلسه با دو مسئله کار کردیم: پیدا کردن بزرگ‌ترین عضو آرایه و جست‌وجو در آرایه، به‌ویژه جست‌وجوی دودویی یا **Binary Search**. ابزار تازهٔ پیچیده‌ای لازم نداریم؛ با آرایه، متغیر، شرط، حلقه و تابع محلی از جلسه‌های قبل جلو می‌رویم.

هدف این نیست که کد نهایی را حفظ کنی. مهم‌تر این است که بتوانی توضیح بدهی چرا یک متغیر لازم شد، چرا یک شرط نوشته شد، چه داده‌ای راه‌حلت را خراب می‌کند و چرا اصلاح پیشنهادی درست است.

اگر پاسخ آماده را می‌فهمی اما هنگام حل تکلیف شروعی پیدا نمی‌کنی، یک فاصلهٔ مشخص برای تمرین داری: **دنبال کردن مسیر دیگری با ساختن مسیر خودت فرق دارد.** این وضعیت به‌تنهایی نشانهٔ ناتوانی یا مناسب نبودن برای برنامه‌نویسی نیست. باید تولید کردن قدم‌های راه‌حل را هم تمرین کنی؛ فقط خواندن مثال‌های بیشتر کافی نیست.

**پیش‌نیاز:** [جلسهٔ سوم](session-03.md) برای آرایه و پیمایش، و [جلسهٔ چهارم](session-04.md) برای ورودی و خروجی متد. هر کادر `csharp` این صفحه را جداگانه در `Program.cs` پروژهٔ Console با top-level statements اجرا کن. از آرایه استفاده می‌کنیم؛ وارد لیست، بازگشت تابع یا ابزارهای آمادهٔ حل این مسئله‌ها نمی‌شویم.

## ۱. قبل از کدنویسی چه کار کنم؟

وقتی صورت مسئله را می‌خوانی، لازم نیست فوراً بدانی کدام حلقه یا شرط را بنویسی. اول این مسیر را روی کاغذ طی کن:

| گام | پرسش | خروجیِ کار تو |
| --- | --- | --- |
| فهم مسئله | دقیقاً چه چیزی از من خواسته شده؟ | یک جمله به زبان خودت |
| ورودی و خروجی | چه می‌گیرم و چه تحویل می‌دهم؟ | نوع داده و یک نمونهٔ جواب |
| حل دستی | بدون کامپیوتر چطور حلش می‌کنم؟ | چند حرکت روی یک مثال کوچک |
| حالت‌های مهم | چه ورودی‌هایی ممکن است فکر اولیه‌ام را خراب کنند؟ | چند نمونهٔ عادی و مرزی |
| حافظهٔ لازم | هنگام حل، چه چیزی را باید به یاد نگه دارم؟ | نام و نقش متغیرها |
| راه‌حل فارسی | چه مراحلی را به‌ترتیب انجام می‌دهم؟ | چند جملهٔ دقیق و قابل اجرا |
| تبدیل به کد | هر جمله با چه ابزار آشنایی نوشته می‌شود؟ | نسخهٔ اولیهٔ برنامه |
| بررسی و اصلاح | کجا انتظار با نتیجه فرق دارد؟ | ردگیری، علت و یک تغییر مشخص |

این گام‌ها دیوار جدا از هم نیستند؛ ممکن است هنگام آزمایش بفهمی صورت مسئله را کامل نفهمیده‌ای و به اول برگردی. این برگشت بخشی از حل مسئله است.

### نمونهٔ اولین جمله

برای بزرگ‌ترین عضو آرایه، جملهٔ «یک حلقه بنویسم» هنوز تعریف مسئله نیست. جملهٔ دقیق‌تر این است:

> یک آرایهٔ عدد صحیحِ غیرخالی می‌گیرم و مقدار بزرگ‌ترین عضو آن را برمی‌گردانم؛ نه اندیس آن را.

این جمله چند تصمیم را روشن می‌کند: ورودی `int[]` است، خروجی `int` است، آرایه باید حداقل یک عضو داشته باشد و جواب، شمارهٔ جایگاه نیست.

## ۲. مسئلهٔ اول · بزرگ‌ترین عضو آرایه

### گام اول: یک نمونه را با دست حل کن

آرایهٔ زیر را در نظر بگیر:

```text
Values:  4   9   2   7
Index:   0   1   2   3
```

اگر عددها یکی‌یکی به تو نشان داده شوند، چطور بزرگ‌ترین را پیدا می‌کنی؟ لازم نیست همه را هم‌زمان حفظ کنی. کافی است **بزرگ‌ترین عددی را که تا این لحظه دیده‌ای** نگه داری.

1. ابتدا فقط ۴ را دیده‌ای؛ پس بهترین مقدار فعلی ۴ است.
2. ۹ را می‌بینی؛ از ۴ بزرگ‌تر است، پس بهترین مقدار را ۹ می‌کنی.
3. ۲ را می‌بینی؛ از ۹ بزرگ‌تر نیست، پس چیزی عوض نمی‌شود.
4. ۷ را می‌بینی؛ باز هم ۹ باقی می‌ماند.
5. عضو دیگری نمانده؛ جواب ۹ است.

ایدهٔ اصلی همین جمله است: «بهترین جواب تا این لحظه را نگه دار و با دادهٔ تازه مقایسه کن.» متغیر `max` از همین نیاز به وجود می‌آید؛ نه از حفظ کردن کد.

### گام دوم: مقدار اولیه را انتخاب کن

چرا از صفر شروع نکنیم؟ این پیشنهاد را با یک مثال نقض بررسی کن:

| ورودی | جواب درست | اگر max را صفر بگذاریم |
| --- | --- | --- |
| `{ 4, 9, 2, 7 }` | ۹ | اتفاقاً جواب درست می‌شود |
| `{ -8, -3, -12 }` | ۳− | صفر می‌ماند؛ در آرایه هم نیست |

یک نمونهٔ موفق، درست بودن همهٔ حالت‌ها را ثابت نمی‌کند. از طرف دیگر، همین یک نمونهٔ منفی کافی است تا پیشنهاد «همیشه از صفر شروع کن» را کنار بگذاریم.

برای آرایهٔ غیرخالی، عضو اول یک انتخاب معتبر است: حتماً در دادهٔ مسئله وجود دارد. پس `max = arr[0]` و بررسی بقیه را از اندیس ۱ شروع می‌کنیم.

### گام سوم: راه‌حل را فارسی بنویس

```text
Input: a non-empty integer array
1. Set max to the first element.
2. Visit each remaining element.
3. If the current element is greater than max, update max.
4. Return max after all elements have been checked.
```

همین مراحل به فارسی: عضو اول را بهترین مقدار فعلی بگیر؛ بقیه را یکی‌یکی ببین؛ اگر بزرگ‌تر بودند جایگزین کن؛ بعد از دیدن همهٔ عضوها، نتیجه را تحویل بده.

### گام چهارم: از جمله به ابزار سی‌شارپ برس

| فکر ما | ابزار در کد |
| --- | --- |
| باید عددی را نگه دارم | متغیر `int max` |
| باید عضوهای باقی‌مانده را ببینم | حلقهٔ `for` از اندیس ۱ |
| فقط گاهی بهترین مقدار عوض شود | شرط `arr[index] > max` |
| نتیجه را بعداً در جای دیگر استفاده کنم | متدی با خروجی `int` و دستور `return` |

### نسخهٔ کامل

```csharp
int FindMaximum(int[] arr)
{
    int max = arr[0];

    for (int index = 1; index < arr.Length; index++)
    {
        if (arr[index] > max)
        {
            max = arr[index];
        }
    }

    return max;
}

int[] numbers = { 4, 9, 2, 7 };

if (numbers.Length == 0)
{
    Console.WriteLine("The array is empty; there is no maximum.");
}
else
{
    Console.WriteLine(FindMaximum(numbers)); // 9
}
```

**قرارداد این تابع:** فقط با آرایهٔ غیرخالی فراخوانی می‌شود. بیرون تابع، قبل از فراخوانی طول را بررسی کرده‌ایم. اگر آرایه خالی باشد، «بزرگ‌ترین عضو» ندارد؛ صفر را به عنوان جواب ساختگی برنمی‌گردانیم. خود تابع، بدون بررسی بیرونی، برای آرایهٔ خالی مناسب نیست چون به `arr[0]` دسترسی دارد. در مثال‌ها ارجاع آرایه موجود است؛ بررسی ارجاع تهی موضوع این درس نیست.

### گام پنجم: ردگیری کن؛ فقط به کد نگاه نکن

| مرحله | اندیس | عضو فعلی | max قبل از مقایسه | تصمیم | max بعد از مقایسه |
| --- | --- | --- | --- | --- | --- |
| مقداردهی اولیه | ۰ | ۴ | — | انتخاب عضو اول | ۴ |
| دور اول | ۱ | ۹ | ۴ | به‌روزرسانی | ۹ |
| دور دوم | ۲ | ۲ | ۹ | بدون تغییر | ۹ |
| دور سوم | ۳ | ۷ | ۹ | بدون تغییر | ۹ |

بعد از هر دور، `max` بزرگ‌ترین عضوِ **بخش بررسی‌شده** است. تا قبل از پایان بررسی، لزوماً بزرگ‌ترین عضو کل آرایه را پیدا نکرده‌ایم. همین جمله به ما کمک می‌کند جای `return` را انتخاب کنیم: بیرون حلقه، پس از دیدن همهٔ عضوها.

### ورودی‌هایی که باید امتحان کنی

| آرایه | نتیجهٔ مورد انتظار | چه چیزی را بررسی می‌کند؟ |
| --- | --- | --- |
| `{ 4, 9, 2, 7 }` | ۹ | حالت عادی |
| `{ -8, -3, -12 }` | ۳− | خطای مقدار اولیهٔ صفر |
| `{ 9, 4, 2 }` | ۹ | بزرگ‌ترین عضو در ابتدا |
| `{ 2, 4, 9 }` | ۹ | بزرگ‌ترین عضو در انتها |
| `{ 5 }` | ۵ | آرایهٔ تک‌عضوی؛ حلقه اجرا نمی‌شود |
| `{ 6, 6, 6 }` | ۶ | مقدارهای برابر |
| آرایهٔ خالی | پیام نبودن عضو، بدون فراخوانی تابع | رعایت قرارداد |

**مکث و تمرین:** پیش از ادامه، کد را ببند و برای `{ 7, 2, 10, 3 }` فقط جدول ردگیری را بنویس. اگر نمی‌توانی بدون نگاه کردن جدول را پر کنی، هنوز لازم نیست سراغ الگوریتم بعدی بروی.

## ۳. خطا را به یک سؤال تبدیل کن

در کلاس، راه‌حل با پیشنهاد، اجرا، دیدن اشکال و اصلاح جلو رفت. برای تکرار همین روند در خانه، هر بار این سه چیز را کنار هم بگذار: **انتظار من، نتیجهٔ واقعی، اولین نقطهٔ اختلاف**.

| پیشنهاد یا خطا | آزمایش کوچک | مشاهده | اصلاح با دلیل |
| --- | --- | --- | --- |
| `max` را صفر بگذاریم | `{ -8, -3 }` | خروجی صفر است، ولی صفر عضو آرایه نیست | از عضو اول شروع کنیم |
| شرط را `arr[index] < max` بنویسیم | `{ 4, 9, 2 }` | مقدار کوچک‌تر انتخاب می‌شود | برای بیشینه باید بزرگ‌تر را انتخاب کنیم |
| بعد از اولین مقایسه return کنیم | `{ 4, 9, 12 }` | جواب ۹ می‌شود و ۱۲ دیده نمی‌شود | بازگشت پس از پایان حلقه باشد |
| شرط حلقه `index <= arr.Length` باشد | `{ 4, 9 }` | تلاش برای دسترسی به اندیس ۲ | آخرین اندیس طول منهای یک است؛ شرط `<` باشد |

خطای نگارشی، خطای زمان اجرا و خطای منطقی را هم از هم جدا کن:

- **نگارشی/کامپایل:** مثل `nt[]` به جای `int[]`؛ برنامه هنوز اجرا نمی‌شود. متن خطا و شمارهٔ خط را بخوان.
- **زمان اجرا:** برنامه ساخته می‌شود، اما مثلاً به عضو خارج از محدوده دسترسی می‌گیرد. مقدار اندیس و طول را بررسی کن.
- **منطقی:** برنامه تمام می‌شود، ولی جواب غلط می‌دهد. نمونهٔ کوچک و جدول ردگیری لازم داریم.

وقتی جواب غلط است، همهٔ شرط‌ها را هم‌زمان تغییر نده. اول کوچک‌ترین ورودی‌ای را بساز که خطا را نشان می‌دهد؛ مقدار متغیرها را دنبال کن؛ سپس فقط تغییری را انجام بده که می‌توانی دلیلش را توضیح بدهی. بعد همان ورودی و آزمایش‌های قبلی را دوباره اجرا کن.

## ۴. مسئلهٔ دوم · آیا یک عدد در آرایه وجود دارد؟

قبل از رفتن سراغ جست‌وجوی دودویی، مسئله را ساده تعریف کنیم:

> یک آرایهٔ عدد صحیح و یک عدد هدف می‌گیرم. اگر هدف در آرایه باشد `true` و در غیر این صورت `false` برمی‌گردانم.

خروجی در این جلسه **وجود یا نبودن** است، نه اندیس عضو و نه تعداد تکرار آن.

### اولین راه‌حل قابل فهم؛ جست‌وجوی خطی

راه دستی این است که عضوها را از ابتدا یکی‌یکی بررسی کنیم. لازم نیست از همان اول بهترین روش را پیدا کنیم.

```csharp
bool Search(int[] arr, int x)
{
    foreach (var item in arr)
    {
        if (item == x)
        {
            return true;
        }
    }

    return false;
}

int[] array = { 2, 5, 8, 10, 13, 19, 22, 44 };
Console.WriteLine(Search(array, 13)); // True
Console.WriteLine(Search(array, 14)); // False
```

`var item` در اینجا از نوع `int` است چون عضوهای آرایه `int` هستند. به محض پیدا شدن هدف می‌توانیم `true` برگردانیم؛ دیدن حتی یک نمونهٔ برابر برای اثبات وجود کافی است. اما برای گفتن «وجود ندارد»، باید همهٔ عضوها را بررسی کرده باشیم؛ پس `return false` بیرون حلقه است.

اگر آرایه خالی باشد، حلقه هیچ دوری اجرا نمی‌شود و نتیجه `false` است. این راه‌حل به مرتب بودن آرایه نیازی ندارد.

**سؤال مهم:** چرا در مسئلهٔ بیشینه نباید زود برگردیم، ولی اینجا گاهی می‌توانیم؟ چون معنای جواب فرق دارد: دیدن یک عضو بزرگ، بزرگ‌ترین بودن آن را ثابت نمی‌کند؛ دیدن یک عضو برابر، وجود داشتن هدف را ثابت می‌کند.

## ۵. جست‌وجوی دودویی؛ از اطلاعات مرتب بودن استفاده کن

برای Binary Search در این درس، آرایه باید **از قبل صعودی مرتب** باشد؛ یعنی هر عضو از عضو قبلی کوچک‌تر نباشد. مقدار تکراری مجاز است. این شرط را بخشی از صورت مسئله بنویس، نه نکته‌ای که بعد از کدنویسی یادت بیاید.

```text
Sorted values:  2   5   8   10   13   19   22   44
Index:         0   1   2    3    4    5    6    7
```

فرض کن عدد ۱۳ را می‌خواهیم. اگر عضو میانی ۱۰ باشد، لازم نیست سراغ سمت چپ آن برویم: همهٔ آن عضوها کوچک‌تر یا مساوی ۱۰ هستند، پس ۱۳ نمی‌شوند. همین اطلاعات به ما اجازه می‌دهد بخشی از گزینه‌ها را کنار بگذاریم.

### سه تصمیم کافی است

| مقایسه با عضو وسط | نتیجهٔ فکری | حرکت بعدی |
| --- | --- | --- |
| هدف برابر عضو وسط است | پیدا شد | `return true` |
| هدف کوچک‌تر از عضو وسط است | عضو وسط و همهٔ سمت راست آن ناممکن‌اند | ادامه در سمت چپ |
| هدف بزرگ‌تر از عضو وسط است | عضو وسط و همهٔ سمت چپ آن ناممکن‌اند | ادامه در سمت راست |

اگر همین کار را روی آرایهٔ نامرتب انجام بدهیم، دلیل حذف کردن یک سمت از بین می‌رود. مثلاً در `{ 8, 2, 10, 5 }` برای پیدا کردن ۸، مقایسه با ۲ ممکن است ما را به سمت راست بفرستد و خود ۸ در سمت چپ حذف شود. بنابراین این روش روی دادهٔ نامرتب **تضمین جواب درست ندارد**؛ حتی اگر برای بعضی هدف‌ها اتفاقاً درست جواب بدهد.

فعلاً مرتب‌سازی را وارد حل نمی‌کنیم؛ ورودی این مسئله از قبل مرتب است. برای دادهٔ نامرتب می‌توانیم همان `Search` را استفاده کنیم.

### متغیرها از کجا آمدند؟

چون هر بار فقط بخشی از آرایه باقی می‌ماند، باید مرز آن بخش را به خاطر بسپاریم:

| متغیر | معنی | مقدار آغازین |
| --- | --- | --- |
| `start` | اولین اندیسِ هنوز ممکن | `0` |
| `end` | آخرین اندیسِ هنوز ممکن | `arr.Length - 1` |
| `mid` | اندیس عضو وسط در محدودهٔ فعلی | در هر دور دوباره حساب می‌شود |

مرزها **شامل خودِ عضوهای ابتدا و انتها** هستند. وقتی `start == end` است هنوز یک عضو داریم، پس باید آن را بررسی کنیم. وقتی `start > end` شد، هیچ عضو ممکنی باقی نمانده است.

دقت کن `start`، `end` و `mid` اندیس‌اند؛ مقدار داخل آرایه `arr[mid]` است. مقایسهٔ هدف با خودِ عدد `mid` به جای `arr[mid]`، مسئلهٔ دیگری را حل می‌کند.

### راه‌حل قبل از کد

```text
1. Keep the whole sorted array as the search range.
2. While the range is not empty:
   - Find the middle index.
   - If the middle value equals the target, return true.
   - If the target is smaller, keep only the left part.
   - Otherwise, keep only the right part.
3. Return false when no candidates remain.
```

هنگام کنار گذاشتن یک سمت، خود عضو میانی هم حذف می‌شود، چون همین حالا فهمیده‌ایم برابر هدف نیست. پس مرز تازه باید `mid - 1` یا `mid + 1` باشد، نه خود `mid`.

## ۶. کد کاملِ بازبینی‌شدهٔ کلاس

منطق اصلی همان منطق کد کلاس است. `nt` به `int` و نام `BinarySerach` به `BinarySearch` اصلاح شده، آکولادها یکدست شده‌اند و بعد از دو حالت اول از `else` استفاده کرده‌ایم؛ چون اگر برابر و کوچک‌تر نبود، در این مقایسهٔ عدد صحیح حتماً بزرگ‌تر است.

```csharp
int[] array = { 2, 5, 8, 10, 13, 19, 22, 44 };

Console.WriteLine(Search(array, 13));       // True
Console.WriteLine(BinarySearch(array, 13)); // True
Console.WriteLine(BinarySearch(array, 14)); // False

bool Search(int[] arr, int x)
{
    foreach (var item in arr)
    {
        if (item == x)
        {
            return true;
        }
    }

    return false;
}

bool BinarySearch(int[] arr, int x)
{
    int start = 0;
    int end = arr.Length - 1;

    while (start <= end)
    {
        int mid = start + (end - start) / 2;

        if (x == arr[mid])
        {
            return true;
        }
        else if (x < arr[mid])
        {
            end = mid - 1;
        }
        else
        {
            start = mid + 1;
        }
    }

    return false;
}
```

### محاسبهٔ وسط

در کلاس از `(start + end) / 2` استفاده شده بود؛ برای آرایهٔ کوچک ما درست است. شکل `start + (end - start) / 2` همان وسط را برای مرزهای معتبرِ این الگوریتم می‌دهد و از جمع مستقیم دو اندیس بزرگ جلوگیری می‌کند. فعلاً لازم نیست وارد جزئیات سرریز عددی شویم؛ مهم این است که بفهمی این عدد، **اندیس وسط محدودهٔ فعلی** است.

تقسیمِ دو عدد صحیح، بخش اعشاری را حذف می‌کند. مثلاً برای مرزهای ۰ و ۷، وسط برابر ۳ می‌شود؛ در تعداد زوج عضوها، اینجا عضو میانیِ سمت چپ انتخاب می‌شود.

ما عضوهای آرایه را حذف یا جابه‌جا نمی‌کنیم؛ فقط `start` و `end` را تغییر می‌دهیم. `mid` در هر دور باید دوباره حساب شود چون محدوده عوض شده است.

## ۷. کد را روی کاغذ اجرا کنیم

### هدف ۱۳؛ عضو وجود دارد

| دور | start | end | mid | arr[mid] | تصمیم |
| --- | --- | --- | --- | --- | --- |
| ۱ | ۰ | ۷ | ۳ | ۱۰ | هدف بزرگ‌تر است؛ start برابر ۴ |
| ۲ | ۴ | ۷ | ۵ | ۱۹ | هدف کوچک‌تر است؛ end برابر ۴ |
| ۳ | ۴ | ۴ | ۴ | ۱۳ | برابر است؛ true |

مسیر کوچک شدن محدوده:

```text
Target: 13
[2, 5, 8, 10, 13, 19, 22, 44]
              [13, 19, 22, 44]
              [13]
              Found
```

بین دو مرز مساوی هنوز عضو ۱۳ را داریم. اگر شرط حلقه فقط `start < end` بود، بررسی این عضو آخر را از دست می‌دادیم.

### هدف ۱۴؛ عضو وجود ندارد

| دور | start | end | mid | arr[mid] | تصمیم |
| --- | --- | --- | --- | --- | --- |
| ۱ | ۰ | ۷ | ۳ | ۱۰ | start برابر ۴ |
| ۲ | ۴ | ۷ | ۵ | ۱۹ | end برابر ۴ |
| ۳ | ۴ | ۴ | ۴ | ۱۳ | start برابر ۵ |
| پایان | ۵ | ۴ | — | — | محدوده خالی است؛ false |

در سطر پایان دیگر `arr[mid]` را نمی‌خوانیم؛ شرط حلقه نادرست شده است. نبودن عدد را بعد از تمام شدن محدودهٔ ممکن نتیجه می‌گیریم.

### چرا حلقه تمام می‌شود؟

هر دور یا عدد را پیدا می‌کند و `return` می‌دهد، یا محدوده را واقعاً کوچک‌تر می‌کند. عضو میانیِ بررسی‌شده دوباره نامزد نمی‌ماند. این دلیلِ پایان یافتن، بخشی از راه‌حل است؛ فقط داشتن یک `while` کافی نیست.

## ۸. چند خطای کوچک، چند درس بزرگ

| خطای پیشنهادی | مثالی که مشکل را نشان می‌دهد | دلیل مشکل |
| --- | --- | --- |
| `start = mid` به جای `mid + 1` | `{ 2, 5 }` با هدف ۵ | وسط صفر می‌شود و start صفر می‌ماند؛ ممکن است حلقه گیر کند |
| `end = mid` به جای `mid - 1` | `{ 2 }` با هدف ۱ | end صفر می‌ماند و همان عضو دوباره بررسی می‌شود |
| شرط `start < end` | `{ 13 }` با هدف ۱۳ | تنها عضو اصلاً بررسی نمی‌شود |
| `end = arr.Length` | `{ 2 }` با هدف ۳ | مرز انتهایی یک واحد بیرون آرایه است و می‌تواند دسترسی نامعتبر بسازد |
| محاسبهٔ mid فقط قبل از حلقه | آرایهٔ کلاس با هدف ۱۳ | مرز عوض می‌شود ولی عضو وسطِ قبلی دوباره خوانده می‌شود |
| `return false` بعد از اولین عضو نابرابر | آرایهٔ کلاس با هدف ۱۳ | نابرابری با یک عضو، نبودن در کل محدوده را ثابت نمی‌کند |
| حذف یک سمت در آرایهٔ نامرتب | `{ 8, 2, 10, 5 }` با هدف ۸ | اطلاعات لازم برای حذف کردن آن سمت وجود ندارد |

نسخهٔ اشتباهِ دارای حلقهٔ بی‌پایان را لازم نیست برای فهم خطا اجرا کنی؛ دو یا سه دور روی کاغذ کافی است تا ببینی متغیرها دیگر تغییر نمی‌کنند. اگر چنین برنامه‌ای را اجرا کردی، اجرای آن را متوقف کن و اول کوچک شدن محدوده را بررسی کن.

### آزمایش‌های ضروری برای BinarySearch

| ورودی و هدف | انتظار |
| --- | --- |
| آرایهٔ کلاس و ۱۳ | True |
| آرایهٔ کلاس و ۱۴ | False |
| آرایهٔ کلاس و ۲ | True؛ اولین عضو |
| آرایهٔ کلاس و ۴۴ | True؛ آخرین عضو |
| آرایهٔ کلاس و ۱ | False؛ کوچک‌تر از همه |
| آرایهٔ کلاس و ۵۰ | False؛ بزرگ‌تر از همه |
| `{ 13 }` و ۱۳ | True |
| `{ 13 }` و ۱۲ | False |
| آرایهٔ خالی و ۱۳ | False؛ end از ابتدا ۱− است |
| `{ 2, 5, 5, 5, 8 }` و ۵ | True؛ فقط وجود را می‌پرسیم |
| `{ -9, -4, 0, 3 }` و ۴− | True؛ عددهای منفی هم قابل جست‌وجو هستند |

در حالت تکراری، خروجی این متد فقط `bool` است؛ قرار نیست اولین یا آخرین محلِ عدد را پیدا کند. مسئلهٔ اندیس را فعلاً به‌عنوان تکلیف جدا از این نسخه در نظر بگیر.

## ۹. خطی یا دودویی؛ فقط شعار «سریع‌تر» حفظ نکن

در جست‌وجوی خطی ممکن است مجبور شویم همهٔ عضوها را ببینیم. در جست‌وجوی دودویی، با هر بررسیِ ناموفقِ وسط، تقریباً نیمی از نامزدها کنار می‌روند. برای آرایهٔ ۸عضویِ مرتب، ممکن است اندازهٔ محدوده به شکل ۸، ۴، ۲ و ۱ کوچک شود.

| موضوع | Search | BinarySearch این جلسه |
| --- | --- | --- |
| ورودی باید مرتب باشد؟ | نه | بله، صعودی |
| فکر اصلی | بررسی عضوها یکی‌یکی | حذف نیمهٔ ناممکن |
| بدترین تعداد عضوهای بررسی‌شده برای ۸ عضو | ۸ | ۴ |
| اولین چیزی که باید درست کنیم | پیمایش و جای return | قرارداد مرتب بودن و حرکت مرزها |

اینجا تعداد **عضوهای بررسی‌شده** را مقایسه می‌کنیم، نه تعداد تک‌تک دستورهای پردازنده. اگر هدف همان عضو اول باشد، روش خطی ممکن است زودتر جواب بدهد. همچنین آماده کردن یک آرایهٔ نامرتب برای جست‌وجوی دودویی خودش کار دارد؛ آن هزینه را رایگان فرض نکن. فعلاً ترتیب یادگیری ما این است: اول راه‌حل درست و قابل توضیح، بعد بررسی فرصت بهتر کردن آن.

## ۱۰. وقتی تکلیف را می‌بینم و هیچ راهی به ذهنم نمی‌رسد

به جای سؤال بزرگِ «کل برنامه را چطور بنویسم؟»، سؤال بعدی را کوچک کن. قرار نیست در اولین دقیقه تمام پاسخ را ببینی.

### وضعیت اول: صورت مسئله را نمی‌توانم توضیح بدهم

هنوز کدنویسی نکن. اسم داده‌ها و جواب خواسته‌شده را روی کاغذ بنویس. مثلاً برای «شمارش عددهای زوج»، روشن کن که جواب **تعداد** است؛ نه چاپ خود عددهای زوج و نه مجموع آن‌ها.

برای `{ 2, 7, 4 }`، جواب ۲ است. اگر نمی‌توانی با دست بگویی چرا، از مدرس دربارهٔ معنای صورت مسئله سؤال کن. پرسیدن دربارهٔ ورودی و خروجی بخشی از حل است.

### وضعیت دوم: صورت مسئله را می‌فهمم ولی روش ندارم

فقط سه داده انتخاب کن و با دست حل کن. هر کاری که انجام می‌دهی را با صدای خودت توصیف کن:

> ۲ زوج است، تعداد فعلی را یک می‌کنم. ۷ زوج نیست، تغییری نمی‌دهم. ۴ زوج است، تعداد را دو می‌کنم.

حالا به جای حدس زدن متغیرها، از روی همین حرف‌ها استخراج کن:

| جملهٔ دستی | نیاز برنامه |
| --- | --- |
| تعداد فعلی را نگه دارم | `count` با شروع صفر |
| تک‌تک عددها را ببینم | حلقه روی آرایه |
| تشخیص بدهم زوج است یا نه | شرط باقی‌ماندهٔ تقسیم بر ۲ |
| در حالت زوج یک واحد اضافه کنم | `count++` |
| بعد از همهٔ عددها تعداد را بدهم | return بیرون حلقه |

این‌بار صفر برای **تعداد** شروع درستی است؛ قبل از دیدن داده‌ها، صفر عدد زوج دیده‌ایم. اما برای **بیشینه** صفر لزوماً درست نبود. مقدار اولیه را از معنای متغیر انتخاب می‌کنیم، نه از یک قانون حفظی.

### وضعیت سوم: روش دستی دارم، ولی نمی‌توانم کدنویسی کنم

مشکل را به ابزار مشخص تبدیل کن: «بلد نیستم روی آرایه حلقه بزنم» یا «نمی‌دانم تابع چه نوع خروجی‌ای لازم دارد». همان بخش کوچک را از جزوه مرور کن و یک نمونهٔ ساده بنویس، سپس به مسئله برگرد.

مثلاً اول فقط آرایه را چاپ کن. وقتی مطمئن شدی همهٔ عضوها دیده می‌شوند، شرط زوج بودن را اضافه کن. بعد شمارنده را اضافه کن. در پایان آن را داخل تابع قرار بده. این مسیر، اجرای کورکورانهٔ کدهای تصادفی نیست؛ در هر مرحله یک سؤال مشخص را جواب می‌دهی.

### وضعیت چهارم: کد دارم، ولی جواب غلط است

برای `{ 2, 7, 4 }` انتظار ۲ داری ولی صفر می‌گیری. قبل از تغییر کد، جدول عضو فعلی و `count` را بساز. آیا شرط برای ۲ درست است؟ آیا شمارنده در هر دور دوباره صفر می‌شود؟ آیا `return` زودتر از موعد اجرا می‌شود؟

**اولین لحظه‌ای که مقدار واقعی با انتظار فرق می‌کند** محل خوبی برای بررسی علت است. آخرین خروجی غلط فقط علامت است؛ معمولاً علت زودتر رخ داده است.

### وضعیت پنجم: جواب را می‌بینم و می‌فهمم، اما فردا باز نمی‌توانم

از پاسخ به‌عنوان راهنما استفاده کن، نه نسخه‌ای برای رونویسی. این چرخه را امتحان کن:

1. قبل از باز کردن پاسخ، تلاش خودت، مثال دستی و محل گیر کردن را ثبت کن.
2. فقط یک راهنمای کوچک بگیر: مثلاً نقش یک متغیر، نه تمام کد.
3. اگر پاسخ کامل را دیدی، توضیح بده هر قسمت کدام نیاز مسئله را برطرف می‌کند.
4. پاسخ را ببند و بعد از یک فاصله، راه‌حل را از صورت مسئله بازسازی کن؛ نه از حفظ ترتیب خط‌ها.
5. یک تغییر کوچک در مسئله بده؛ مثلاً به جای شمارش زوج‌ها، تعداد عددهای بزرگ‌تر از هدف را پیدا کن.
6. خروجی را با آزمایش‌ها بررسی و دلیل هر تصمیم را دوباره توضیح بده.

بازسازی از حافظه و سپس بررسی خطاها، به‌جای نگاه مداوم به پاسخ، یک روش تمرین بازیابی است. برای شرح کوتاه این شیوه می‌توانی [راهنمای تمرین بازیابی](https://www.learningscientists.org/blog/2016/6/23-1) را ببینی. اینجا هدفِ بازسازی، توضیح **دلیل مراحل** است، نه حفظ کردن کد.

اگر در بازسازی گیر کردی، لازم نیست همان‌جا کل پاسخ را دوباره بخوانی؛ اول مثال دستی را بساز. اگر هنوز حل نشد، یک راهنمای محدود بگیر و مرحلهٔ بعد را خودت انجام بده.

## ۱۱. تمرین مؤثر دقیقاً چه شکلی است؟

صرف زیاد بودن ساعت یا تعداد تکلیف، معیار کافی نیست. برای هر تمرین، یک چرخهٔ کاملِ **تلاش، بازخورد و اصلاح** بساز.

### یک برگه برای هر مسئله

می‌توانی این الگو را در دفترت کپی کنی:

| بخش | چیزی که باید خودت بنویسی |
| --- | --- |
| صورت مسئله به زبان من | یک جملهٔ روشن |
| ورودی و خروجی | نوع، قرارداد و نمونه |
| مثال دستی | حداقل یک ورودی کوچک با جواب |
| حالت متفاوت | منفی، تک‌عضوی، خالی، تکراری یا نبود هدف؛ بسته به مسئله |
| راه‌حل فارسی | مراحل به‌ترتیب |
| نقش متغیرها | هر متغیر چه چیزی را به یاد می‌سپارد؟ |
| آزمایش | انتظار و خروجی واقعی |
| اشتباه امروز | علت، مثال نقض و اصلاح |
| تلاش بعدی | یک تغییر کوچک برای حل مستقل |

نوشتن این برگه کار اضافهٔ بی‌هدف نیست؛ تمرینِ همان بخش‌هایی است که معمولاً بین خواندن صورت مسئله و نوشتن کد گم می‌شوند.

### تمرین را به اندازهٔ مرحلهٔ خودت کوچک کن

اگر هیچ پیش‌زمینه‌ای نداری، ابتدا فقط ورودی و خروجی و حل دستی را تمرین کن. بعد حلقهٔ ساده را به کد تبدیل کن. می‌توانی در جلسهٔ تمرین اول فقط یک مسئله را با همین روند جلو ببری.

اگر برنامه‌نویسی کرده‌ای اما مسئله‌حل‌کردن هنوز سخت است، مستقیم به سراغ کد کوتاه‌تر نرو. برای انتخاب شرط، مقدار اولیه و محل `return` دلیل بنویس. سعی کن یک مثال پیدا کنی که راه‌حل اشتباه اولیه‌ات را خراب می‌کند.

هدف برای هر دو گروه یکسان است؛ اندازهٔ قدم‌ها و مقدار راهنمایی می‌تواند متفاوت باشد.

### تمرین را در چند نوبت پخش کن

این یک برنامهٔ پیشنهادی است، نه زمان‌بندی اجباری یا تضمین پیشرفت در چند روز:

| نوبت | تمرکز | چیزی که تحویل خودت می‌دهی |
| --- | --- | --- |
| اول | بیشینه با کمک جزوه | مثال دستی، کد و جدول ردگیری |
| روز بعد | کمینه بدون دیدن کد بیشینه | راه‌حل مستقل و آزمایش با منفی‌ها |
| نوبت بعد | جست‌وجوی خطی و شمارش رخداد | توضیح تفاوت «پیدا شدن» و «چند بار بودن» |
| نوبت بعد | Binary Search روی کاغذ | ردگیری برای هدف موجود و ناموجود |
| نوبت بعد | بازنویسی و اشکال‌زدایی | کد، آزمایش‌های مرزی و یک خطای توضیح‌داده‌شده |

اگر یک نوبت را نتوانستی انجام بدهی، اندازهٔ تمرین را کمتر کن؛ لازم نیست همه را در یک نشست طولانی جبران کنی. تمرین کوتاهی که در آن خودت تصمیم می‌گیری و بازخورد می‌گیری، از رونویسی بدون فکر مفیدتر است.

### چگونه کمک بخواهم؟

به جای «هیچی بلد نیستم، کدش را بده»، یک گزارش قابل بررسی آماده کن:

> ورودی من `{ -8, -3 }` است. انتظار دارم جواب `-3` باشد، اما `0` می‌گیرم. max را از صفر شروع کرده‌ام و بعد از دو دور هم عوض نمی‌شود. آیا مشکل از مقدار اولیه است؟

برای سؤال پرسیدن لازم نیست علت را از قبل فهمیده باشی؛ داشتن ورودی، انتظار، نتیجه و تلاش فعلی کافی است تا مدرس بداند چه راهنمایی‌ای لازم داری. از هم‌کلاسی یا ابزار کمکی هم بخواه **یک سؤال راهنما یا یک ورودی آزمایشی** بدهد، نه کل پاسخ.

**قاعدهٔ پیشنهادی هنگام گیر کردن:** بعد از یک تلاش متمرکز، اگر هیچ قدم تازه‌ای پیدا نمی‌کنی، مسئله را کوچک‌تر کن یا کمک محدود بگیر. خیره شدن طولانی به صفحه بدون تغییر روش، خودش تمرین حل مسئله نیست. زمان دقیق برای همه یکی نیست؛ معیار، داشتن تلاش مشخص و بازخورد است.

## ۱۲. تمرین‌های مرحله‌ای؛ از نزدیک‌ترین مسئله شروع کن

برای هر تمرین، قبل از نوشتن کد، ورودی و خروجی و یک حل دستی بنویس. جواب کاملِ مسئله‌های جدید این بخش را عمداً نمی‌آوریم؛ راهنماها کمک می‌کنند قدم بعدی را خودت بسازی. خروجی مورد انتظار برای بررسی نتیجه است، نه جایگزین توضیح راه‌حل.

### مرحلهٔ اول · تغییر کوچک در مسئلهٔ آشنا

**۱. کمینه:** تابعی بنویس که کوچک‌ترین عضو آرایهٔ غیرخالی را برگرداند. برای `{ 7, -2, 9, 0 }` انتظار `-2` و برای `{ 4 }` انتظار `4` داریم. بیرون تابع، آرایهٔ خالی را قبل از فراخوانی تشخیص بده.

<details>
<summary>راهنمای اول: چه چیزی باید به یاد بماند؟</summary>
<p>کوچک‌ترین عددِ بخش بررسی‌شده را نگه دار. قبل از دیدن عضوها، صفر لزوماً کوچک‌ترین نیست.</p>
</details>
<details>
<summary>راهنمای دوم: نسبت آن با بیشینه چیست؟</summary>
<p>از عضو اول شروع کن. این بار از خودت بپرس چه وقت باید مقدار کوچک‌تر جای مقدار فعلی را بگیرد. قبل از نگاه به کد بیشینه، شرط را فارسی بنویس.</p>
</details>

**۲. شمارش عددهای زوج:** برای `{ 2, 7, 4, -6, 0 }` انتظار `4` است. برای آرایهٔ خالی انتظار صفر داریم. خروجی تعداد است؛ خودِ عددهای زوج را به عنوان جواب چاپ نکن.

<details>
<summary>راهنما: مقدار اولیه و تغییر آن</summary>
<p>قبل از دیدن داده‌ها، هیچ عدد زوجی ندیده‌ای. برای هر عضو با باقی‌ماندهٔ صفر در تقسیم بر ۲، یک واحد به تعداد اضافه کن. نتیجه پس از پایان پیمایش معلوم می‌شود.</p>
</details>

**۳. شمارش بزرگ‌ترها:** یک آرایه و یک هدف بگیر و تعداد عضوهای بزرگ‌تر از هدف را برگردان. برای `{ 3, 8, 8, 1 }` و هدف `5` انتظار `2` است. عضو مساوی هدف نباید شمرده شود.

### مرحلهٔ دوم · یک معنای تازه برای خروجی

**۴. تعداد رخداد:** برای `{ 2, 5, 5, 8, 5 }` و هدف `5` انتظار `3` است. برای هدف `9` و آرایهٔ خالی انتظار صفر داریم. توضیح بده چرا اینجا نمی‌توانیم مثل `Search` با اولین عضو برابر کار را تمام کنیم.

**۵. اولین اندیس:** جست‌وجوی خطی را طوری تغییر بده که اندیس اولین عضو برابر را برگرداند؛ اگر پیدا نشد `-1` بدهد. برای آرایهٔ تمرین قبل و هدف `5` انتظار `1` است. جواب `0` هم می‌تواند اندیس معتبر باشد، پس آن را برای «پیدا نشد» انتخاب نکن.

**۶. بیشینه کجاست؟** اندیس اولین رخداد بزرگ‌ترین مقدار را در آرایهٔ غیرخالی برگردان. برای `{ 9, 3, 9, 2 }` انتظار `0` است. مشخص کن مقایسهٔ «بزرگ‌تر» و «بزرگ‌تر یا مساوی» چه اثری بر حفظ اولین رخداد دارند.

<details>
<summary>راهنما: مقدار و اندیس را قاطی نکن</summary>
<p>ممکن است یک متغیر برای بهترین اندیس کافی باشد و مقدار بهترین عضو را با همان اندیس بخوانی. ابتدا روی کاغذ جایگاه‌ها و مقدارها را در دو ردیف جدا بنویس. راه‌حل با دو متغیر هم قابل قبول است، اگر نقش هرکدام روشن باشد.</p>
</details>

### مرحلهٔ سوم · فهمیدن حرکت مرزها

**۷. ردگیری بدون اجرا:** برای آرایهٔ کلاس، هدف‌های `2`، `44`، `14` و `1` را جست‌وجوی دودویی کن. برای هر دور، `start`، `end`، `mid` و `arr[mid]` را بنویس. بعد از تکمیل جدول، با برنامه مقایسه کن. انتظار خروجی‌ها به‌ترتیب `True`، `True`، `False` و `False` است.

**۸. پیدا کردن علت گیر کردن:** روی کاغذ، در آرایهٔ `{ 2, 5 }` و هدف `5` به جای `start = mid + 1` بنویس `start = mid`. دو دور را حساب کن و توضیح بده چرا دور بعد هم تغییری نمی‌کند. بعد نسخهٔ درست را بنویس. نیازی به اجرای نسخهٔ بی‌پایان نیست.

**۹. عضو آخرِ باقی‌مانده:** شرط حلقه را روی کاغذ به `start < end` تغییر بده. آرایهٔ `{ 13 }` و هدف `13` را بررسی کن. توضیح بده چرا مساوی بودن مرزها نباید باعث توقف زودهنگام شود.

**۱۰. مرتب بودن چه کمکی می‌کند؟** برای `{ 8, 2, 10, 5 }` و هدف `8` نشان بده روش دودویی چه چیزی را به‌اشتباه کنار می‌گذارد. همان داده را با `Search` بررسی کن. به جای تغییر تصادفی شرط‌ها، بنویس کدام قرارداد مسئله رعایت نشده است.

### مرحلهٔ چهارم · ساختن یک راه‌حل مستقل

**۱۱. آزمایش دو روش:** یک آرایهٔ مرتب مثل `{ -4, 0, 3, 3, 9 }` بساز. با یک حلقه، هدف‌های `-5` تا `10` را به هر دو تابع بده. نتیجهٔ `Search` و `BinarySearch` باید برای هر هدف یکسان باشد. اگر اختلاف دیدی، همان آرایه و هدف را در جدول ردگیری بررسی کن. این آزمایش کمک‌کننده است، ولی به‌تنهایی اثبات درستی برای همهٔ ورودی‌های ممکن نیست.

**۱۲. تمرین ترکیبی:** تابعی بنویس که تعداد عضوهای آرایه را که از **میانگین آرایه** بزرگ‌ترند برگرداند. برای `{ 2, 4, 6 }` میانگین ۴ و جواب `1` است. برای `{ 5, 5 }` جواب صفر است. قرارداد را آرایهٔ غیرخالی بگذار و بیرون تابع ورودی خالی را بررسی کن. مقدارها کوچک‌اند تا مجموع در `int` جا شود؛ برای میانگین از تقسیم اعشاری استفاده کن.

<summary>راهنمای اول: آیا با دیدن عضو اول، میانگین را می‌دانی؟</summary>
<p>نه؛ برای محاسبهٔ میانگین، اول مجموع و تعداد لازم است. سپس می‌توانی عضوها را با میانگین مقایسه کنی. لازم نیست خودت را به یک حلقه محدود کنی.</p>
</details>

<summary>راهنمای دوم: مسئله را به دو کار کوچک تبدیل کن</summary>
<p>یک بار برای مجموع حرکت کن و میانگین را حساب کن. سپس بار دیگر برای شمارش عضوهای بزرگ‌تر از میانگین حرکت کن. می‌توانی محاسبهٔ میانگین را در یک تابع جدا قرار بدهی، اما اول راه‌حل فارسی را روشن کن.</p>
</details>

## ۱۳. از کجا بفهمم دارم پیشرفت می‌کنم؟

پیشرفت فقط «تکلیف تمام شد» نیست. این موارد را با تلاش قبلی خودت مقایسه کن، نه با سرعت هم‌کلاسی‌ای که قبلاً برنامه‌نویسی کرده است:

- می‌توانم صورت مسئله را بدون تکرار کلمه‌های مبهم توضیح بدهم.
- قبل از اجرا، برای یک ورودی کوچک جواب مورد انتظار می‌نویسم.
- می‌دانم هر متغیر چه نقشی دارد و چرا مقدار اولیه‌اش را انتخاب کرده‌ام.
- می‌توانم یک دور حلقه را روی کاغذ دنبال کنم.
- برای یک راه‌حل اشتباه، مثال نقض می‌سازم و علت را توضیح می‌دهم.
- با راهنمای کوچک جلو می‌روم و وابستگی‌ام به پاسخ کامل کمتر می‌شود.
- بعد از فاصله، یک مسئلهٔ مشابه را با داده یا خروجی متفاوت حل می‌کنم.

**معیار پایان جلسه:** لازم نیست از حفظ Binary Search را تایپ کنی. باید بتوانی برای بیشینه و جست‌وجو، قرارداد ورودی را بگویی، از یک نمونه به مراحل حل برسی، اجرای کد را ردگیری کنی و برای هر اصلاح دلیل بیاوری. اگر هنوز بخشی سخت است، همان مهارت کوچک را با مثال ساده‌تر تمرین کن.

> حل مسئله با دیدن پاسخ نهایی تمام نمی‌شود؛ جایی رشد می‌کند که خودت یک تصمیم می‌گیری، آن را امتحان می‌کنی و از نتیجه برای قدم بعد استفاده می‌کنی.
